# Architecture

[中文](zh-CN/architecture.md) · [README](../README.md)

Workboard is a trusted Paseo plugin with separate client and server entries. The daemon owns task data and automation. Each client renders the selected host's board or grouped list and keeps only its display preferences locally.

## Modules

| Location                                          | Responsibility                                                                   |
| ------------------------------------------------- | -------------------------------------------------------------------------------- |
| `index.client.tsx`                                | Sidebar, settings screen, Command Center entry and query provider                |
| `client/`                                         | Board and list views, forms, filters, drag interactions, themes and translations |
| `index.server.ts`                                 | Settings registration, RPC handlers and server lifecycle                         |
| `server/workboard.ts`                             | Reconciliation, serialized mutations, binding, pinning and archive decisions     |
| `server/host.ts`                                  | Paseo inventory, subscriptions, history and workspace operations                 |
| `server/paseo-compat.ts`                          | Access to host operations missing from the public SDK                            |
| `server/conversations.ts`, `server/git-safety.ts` | Conversation timestamps and pre-archive checks                                   |
| `server/store.ts`, `shared/migrations.ts`         | Revision-checked persistence and data migration                                  |
| `shared/model.ts`, `shared/rpc.ts`                | Zod models, settings and RPC contracts                                           |

## Identity and state

A task has a plugin-generated ID. An unbound draft has no `workspaceId`; a bound task is unique by host and workspace ID. Names, branches and paths do not establish identity. Multiple agents in one workspace remain one task.

The daemon imports every active workspace across all pages. A workspace without a managed group label enters the configured default group without a label write, falling back to the first Inbox group when the configured destination is absent, unset or terminal. Default destinations exclude Done/Canceled; saving such a default or changing the selected group to a terminal type is refused without making stored data unparseable. Explicit managed labels select groups; multiple managed labels produce a visible conflict. Unrelated labels are preserved. Archived workspaces that Workboard never observed are not backfilled.

Groups have stable IDs, a name, a managed label, a semantic type and an optional color. Display order and color are independent of type. Types control draft destinations, in-progress sidebar pinning and terminal archive eligibility. At least one Inbox, Todo and Canceled group remain. Deletion distinguishes task occupancy from default destination use, requiring tasks to be moved or the default to be changed. New drafts may default to any Todo-type group; absent or invalid destinations keep the first-by-type fallback. Start work separately resolves `defaultStartWorkGroup` to a configured In progress group, then the first such group, or no destination. Both StartModal and the server use this resolver, preserving pending binding and explicit-stage intent. `defaultStartGroup` carries only the unlabeled-import meaning. A missing start-work preference defaults to null and never copies the import default. Kind/ID validation happens when saving settings; invalid stored preferences remain readable. Client deletion hints and server validation require switching an explicitly selected working default before deleting its group or changing its type.

Agent activity is a separate projection. A reply finishing never marks a task done. Workspace activity combines only unarchived, non-delegated Agents in the order waiting, error, attention, running, idle. Both directory inventory and subscription upserts map Paseo's `paseo.parent-agent-id` label to `Agent.delegatedBy`. Agents with a nonempty `delegatedBy` are excluded from this aggregation, including its running state; the card's activity, activity filters and activity reasons for Needs attention use that result. Provider children use `parentAgentId` and remain included.

Among the included Agents, an error is excluded from this projection only when the native Agent has `status: idle`, a nonempty `lastError`, and no error attention reason, and another included, non-error Agent has a `lastUserMessageAt` strictly later than the errored Agent's `updatedAt`. The latter is used as an upper bound, never as evidence of healthy activity: metadata edits can advance it. Invalid or missing evidence retains the error. Native error status, error attention, failed provider children and unknown error sources remain actionable within this set. Individual Agent details retain their original activity, including delegated Agents. Delegated Agents also remain in conversation evidence and archive safety checks; their running or waiting states still defer archive. PR/MR information comes from Paseo's workspace data; Workboard does not poll forge services or implement a separate merge detector.

## Persistence and concurrency

Host settings store schema version 10 (declared once in `shared/model.ts`), including tasks, groups, preferences, binding/archive intents and owned pin timestamps. The conversation record keeps display evidence and gate evidence apart, archive rules carry their own delays, default destinations are stored per use, and merged drafts are recorded per task. The store validates data and writes against the host settings revision. Migrations preserve existing records; unsupported or invalid data stops initialization and automatic retries, with a visible board error. Transient connection failures still retry every ten seconds. Data is never silently replaced.

A missing exclusive-status preference in migrated data is held off with a persisted pending flag. The first successful full workspace inventory decides it once: any managed-label conflict keeps exclusivity off; no conflicts enables it. Reconciliation reuses its label resolution pass and saves the decision with task state before any automatic label resolution. Failed inventory reads leave the decision pending. After an unconfirmed write, reloading persisted state determines whether the decision was saved or still needs to run. Explicit preferences are preserved, and fresh data defaults to on.

Every migration is a pure step in the `shared/migrations.ts` chain, must be idempotent on current data, and must keep old records usable. Rules:

- Never drop a record that still carries information, and never invent data the old values cannot prove. Agent IDs without observation times or provider child IDs are dropped only when they are unfilled placeholders; a cached provider child keeps its entry even without a message timestamp or a live marker.
- Per-state archive rules come from the previous shared values: each rule keeps `autoArchive && ruleEnabled` and retains every delay, so a migrated workspace can stay eligible for automatic archive. Fresh settings default both rules off.
- Ambiguous archive meaning may only resolve toward less destructive behavior in the specific repair where migration cannot inspect host state. When a settings record has no Canceled group, the v6→v7 step adds one and turns automatic archive off, because it cannot tell whether existing workspaces should have been canceled; a persisted `archiveMappingNeedsReview` flag keeps that explanation visible until archive is re-enabled through the due-task confirmation flow. Other migrations retain the original preference.
- Bump the schema version whenever stored shape or meaning changes, and cover the new step with a migration test from every version it accepts.

Task ordering for both views lives in the v8 Data and Board top-level `cardOrderByStage` map, separate from task records and settings. Both client and server use the shared pure sorter. Reorder/reset mutations compare the complete unfiltered projected column inside the server serial queue and Store update; only archived/external records are hidden, while pending/uncertain archives and bindings remain as immovable neighbors. Reordering moves one eligible task, retains every other task's relative order, and writes only the order map. Missing IDs are ignored until they return; a subsequent reorder compacts current membership. Deleting a group clears its key. v7→v8 defaults the map to empty, and older migrations continue through that step.

One server-side queue serializes mutations and reconciliation. Subscriptions coalesce affected workspace changes, and a 60-second refresh reconciles missed events. Polling clients do not own archive timers. The client uses optimistic stage changes, then confirms or rolls back using the server result.

Group edits and ordering use expected configuration values to reject stale writes. Task edits check `updatedAt`; status changes check the managed labels they were based on. Concurrent native edits can still occur after the final check because the supported hosts do not provide a conditional atomic label/archive operation.

Client writes track pending control IDs, rejecting repeat submissions from that control with localized feedback while allowing unrelated requests. The server remains responsible for optimistic concurrency. Mutation responses only replace cached data when their revision is at least as new as the cache. Confirmations retain a visible failure slot on false results or exceptions. Error text maps every static server error and known issue, with a localized generic fallback for dynamic or unknown errors.

Successful cross-group moves share an eight-second task highlight and a toolbar feedback bar for the most recent move, available across views and even when the task is filtered out or its group is collapsed. Undo sends only a reverse `stage` mutation with the successful managed labels as its expectation. Polling card changes or expiry invalidate it; a native label conflict rejects it visibly. It does not change archive paths or bypass gates. Conflict resolution lacks a single previous group and cannot use this reversal; group ordering keeps its existing reverse-by-reordering interaction.

The board and list share one query, filters, task and group order, optimistic state, pending writes, and undo logic. List groups scroll vertically and retain empty groups, matched/total counts, collapsed drop targets, and independent fold state. List drop geometry uses content coordinates and visible task anchors; the server still checks the full unfiltered order. A board drop expands a collapsed target column, while a list drop leaves the target collapsed. Quick-create text and errors are keyed by group above the view switch, so switching or folding cannot discard them; only a successful create clears the text. Switching views does not cancel submitted writes. Filters update the controlled view immediately and debounce client storage by 300ms, flushing dirty values when leaving. Conflict notices use the same filters and separate counts. Board column header reorder requires Alt/Meta arrows; list handles use Alt+Up/Down, with menu up/down actions as an alternative. Unfinished drags cancel on Escape, window blur, view switch, or filter change. The board column action label describes group options; drag instructions are separate hints. Tooltip timers clear on dismissal/unmount. The native settings surface omits board navigation.

## Draft binding

Creating a draft writes only plugin data. A create request may select any Todo-type group; omitted groups use the default Todo target.

Starting work persists an operation ID and uses Paseo's idempotent workspace creation. It either creates a workspace without an agent or attaches an existing one. The workspace link is retained if label synchronization fails, so retrying does not create another workspace. Attaching an already imported workspace merges the draft into its existing card and preserves notes while recording the original draft ID, title, description, merge time and appended text. `detach-draft` checks the surviving task’s `updatedAt`, removes only a unique match of the original appended text, restores an unbound draft with its original ID, and removes that source record. Multiple sources can be restored independently. Edited or ambiguous text, an occupied original ID, or an archived survivor rejects the operation while keeping its data and source records. A failed binding can be retried or canceled using its expected operation ID. Cancellation rejects executing or queued bindings and retains any created or linked workspace.

## Automation safeguards

Sidebar pinning is enabled by default and follows the `in-progress` group type. Workboard records the exact `pinnedAt` value returned by Paseo. It removes only a pin it still owns; an existing or manually replaced pin remains. A user removing an automatic pin suppresses repinning until the task leaves and re-enters that type.

Automatic archive is disabled by default. Done and Canceled groups have independent enable flags and delays. Each enabled rule requires strictly more than its configured delay (30 days by default, an integer from 1 to 365) since the latest verified user or assistant message across the workspace's agents. A missing per-state delay falls back to the shared `archiveAfterDays` value. Changing labels, editing notes or importing a workspace does not reset this clock. Drafts and workspaces without a trustworthy conversation bound do not qualify.

Each agent's conversation is stored as two separate values: the time a card shows, and the gate automatic archive may use. Display evidence is either an exact user or assistant message, a lower bound (`≥`, Paseo's recorded user message or the oldest rows of a partially replayed window) or an upper bound (`≤`, Paseo's recorded activity). Gate evidence is exact, or Paseo's recorded activity as an upper bound, which is never earlier than the real last message and therefore can only delay an archive. A lower bound never gates. When a trustworthy inventory first shows zero Agents, Workboard records that observation time in memory as an upper bound, not an exact conversation time. Continuous trustworthy empty inventories keep the same bound, including the archive recheck; task edits and label changes do not move it. Seeing an Agent, Agent/provider lifecycle events (even a create-delete between inventories), restart, disconnect, subscription loss or resnapshot, and failed inventory reads discard it and restart the waiting period on the next trustworthy empty inventory. Recorded children and an unknown gate with an unresolved failure still keep the gate unknown; the displayed reason may summarize multiple failures, including child enumeration. Deleting the last Agent does not erase that risk. Paseo re-stamps replayed history with the hydration moment, so rows newer than the recorded activity are dropped as hydration stamps instead of failing the workspace; a recorded observation also stays a lower bound, never a gate.

If a parent's provider children cannot be enumerated, the workspace's archive gate is unknown, even if the parent has an old activity timestamp or previously observed children. Child activity need not update the parent. Display evidence is retained, but automatic archive waits for complete child inventory and usable conversation evidence. An enumerated child without a proven conversation upper bound also blocks the gate; a verified empty timeline does not. The same check applies after a restart and immediately before archival.

A previously observed child missing from the current inventory makes the gate unknown. Its last read, even an exact time, upper bound or empty history, cannot cover messages arriving before removal. Stored child observation times remain display evidence across refreshes and restarts, including for records stored before child IDs were kept; they never authorize archive. No additional child gate fields are persisted. A verified empty read exempts only a child still in the current inventory and does not make an otherwise empty workspace eligible.

Restored subscription snapshots and subscription request failures invalidate cached child inventories. Provider child updates invalidate their parent's cache. Invalidation retains observed children until a fresh listing succeeds; an in-flight response from before invalidation cannot repopulate the cache or make the current inventory complete, including parents already read in that pass. Failed enumeration for an active (running or waiting) unarchived parent is retried after a fixed 60 seconds, even if its activity timestamp has not changed. An idle parent is not enumerated by a refresh at all; only the archive recheck lists it, and its failures back off exponentially (one minute doubling to one hour, see below). Archived parents remain unenumerable.

Paseo loads an agent before it answers any per-agent request (timeline, provider child list, child timeline), and nothing unloads an idle agent. A refresh therefore sends those requests for active agents only (running or waiting). An idle, unarchived parent is not enumerated: its children are marked skipped, which is not the failed enumeration that is retried after 60 seconds, so an idle parent is never retried on a timer. The gate of such a workspace stays unknown and the card shows its recorded bound (`≥`/`≤`) with a note that the agent is idle. A recorded child absent from the inventory of a skipped parent is not a vanished child; it is missing only because the parent was not listed. Children that disappear from a complete listing, an archived parent and a failed listing keep the rules above.

An idle parent's recorded time, together with any stored child observation times, only schedules a recheck: once it is due under the group's rule and nothing but skipped idle parents keeps the gate unknown, the workspace becomes a recheck candidate. It never authorizes an archive. The recheck lists every idle parent's children fresh (a failed listing, or an invalidation during it, defers), reads the idle agents and every listed child, and archives only when each of them has a usable bound and the result is due. A busy child is judged from this fresh listing. The recheck may load idle agents even when it ends by deferring; they stay loaded until closed. Newer child times found by a recheck are stored in the existing child observation time, which never authorizes an archive but moves the next scheduled recheck past them, so neither repeated refreshes nor a restart repeat the same reads. A failed recheck backs off in memory (one minute doubling to one hour); a restart clears that backoff, so a still-failing due candidate is tried once more after each restart.

Workboard runs on the real clock. The isolated integration suite can ask for a test-only offset (`WORKBOARD_TEST_CLOCK_OFFSET_MS`) so freshly created fixture Agents count as old; it is honored only when the Paseo home is a temporary directory that holds the integration marker, and otherwise ignored without any message. With `WORKBOARD_TEST_CLOCK_FILE=1` as well, the marked-home tests can advance the offset through the fixed `.workboard-clock-offset-ms` file in that home without restarting the plugin. Only nonnegative integer offsets at least as large as the last accepted offset are accepted; missing, invalid or decreasing values retain that offset. Production clocks never read this file. The snapshot reports the current offset, and the client uses it for every due-date calculation (settings preview, card due dates), so what it shows matches what the server decides.

The server rechecks labels, activity and workspace safety before calling native archive. Active agents, terminals, scripts, history without a provable bound or unsafe Git state defer the operation. Git checks do not repair the working tree or push changes. The persisted archive intent becomes uncertain after a timeout or interrupted operation; it is not blindly retried. Success requires a native success response and disappearance from a refreshed active workspace list.

Blocked candidates back off in memory by reason, doubling from one minute to a maximum of one hour. Relevant inventory changes trigger rechecking, and a different reason observed during a check resets the delay. Deferred tasks reuse conversation evidence without repeated timeline replay or Git checks. Each scan shares one inventory read; pre-send and post-success confirmations remain independent. Restart clears the backoff. Settings saves atomically clear only inapplicable deferrals' owned warnings, then discard those deferrals after persistence succeeds. Reconciliation also checks applicability before honoring backoff. A disabled rule or a known gate that is no longer due proves inapplicability; an unknown gate alone does not. Independent task issues are retained, and preference saves do not re-read conversation history.

The archive page can confirm uncertain or external outcomes as archived, or clear their record and return the task to the board. Requests check the task update timestamp and archive operation ID; restoration to a deleted group is refused while its record is retained. User confirmation does not call native archive or invent a native archive time. Restoration retains the workspace association; an absent workspace shows as unavailable while the task stays on the board until native inventory rediscovers it. It does not restore a native workspace or directory. All automatic archive gates still apply. Archived drafts can also be restored using the same timestamp and operation ID checks. They return to the original group after clearing the archive record; deletion or a type that no longer accepts drafts blocks restoration and keeps the record.

Native archive may stop agents/terminals and remove a managed worktree. Workboard records archive status but does not guarantee directory cleanup or restoration. Paseo's independent archive-on-merge setting remains under Paseo's control.

## Compatibility boundary

The public SDK does not expose every required operation. The compatibility module uses the plugin's existing authenticated IPC session for labels, pins, settings writes, bootstrap and selected history/record queries. It does not create a second login, replace credentials or modify Paseo.

The manifest owns the minimum Paseo version. The bridge validates response shapes but does not pin a host version. Later versions may require a compatibility change. The CI host matrix in `.github/workflows/ci.yml` declares which Paseo versions the pipeline is configured to test; a matrix entry shows intent, not a passing result, and only an actual green run supports a compatibility claim. State any supported range change and its remaining limits in the README, the Cafe listing, and the notes of the Release that makes the change.

The runtime uses the fixed plugin ID `paseo-workboard`; install it without an `--id` override.

Client imports use Paseo-provided React, React Native, TanStack Query, Zod and plugin modules. The server uses the provided SDK/Zod and Node built-ins. The published package contains TypeScript sources; Paseo prepares them, so there is no build step or runtime npm dependency installation.

## Client preferences

Paseo has no public plugin locale API. `client/paseo-language.ts` reads the Web/Electron app's `@paseo:app-settings` language, with its legacy key as a fallback, without writing host settings. It uses Paseo's system-locale selection rules and translates Chinese or English. While a surface is mounted, storage/focus events and a one-second check observe changes in the same window. Revalidate this private storage contract when upgrading Paseo. Clients without that storage, including native mobile, fall back to English.

View choice defaults to Board, and list collapsed groups start expanded. View choice, separate board/list collapsed groups, board column widths, and filters are stored per host in browser `localStorage`, independently from daemon settings. View preferences do not add RPC or data-schema fields. Storage failures leave the current view usable. These preferences are not synchronized between clients. Native mobile persistence and touch behavior are outside the supported platform coverage.
